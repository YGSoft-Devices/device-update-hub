# Accounts and Synology Backups

## Migration and First Account

Application 0.2.0 adds accounts and encrypted Synology backups. Catalog schema 3 is an atomic additive migration from 2; preserve a stopped complete-data schema-2 backup before installation. Old binaries cannot open schema 3. Update the trusted external agent before a schema-3 package; failed installation restores the previous complete volume before restarting 0.1.1. Never rebuild frozen releases. Existing file-backed tokens remain compatible and independent of user accounts.

Sign in over HTTPS with the deployment admin token, open **System > Users**, and create an enabled named **Admin** with a unique password of at least 15 characters. Sign out, select **Password**, and verify it. Store credentials outside chat/source/logs. The protected original credential file remains an operator bootstrap/recovery mechanism; disabling a database user does not revoke those independent file credentials. Their retirement needs a separately verified recovery plan.

Admins create/edit/disable users, reset passwords, revoke sessions and issue/revoke expiring named API tokens. Accounts/audit identities are retained, not hard-deleted. Publisher/reader users require explicit existing-product grants; admins have no per-product grants. The last enabled database admin cannot be disabled/demoted. Edits revoke sessions; username/role/grant/enabled-state changes also revoke API tokens. Password resets/changes revoke all sessions and tokens. **Account** supports self-service password change; sign in again afterward. Email recovery, MFA and SSO are excluded.

Argon2id uses 64 MiB, three iterations and one lane, with two concurrent password operations maximum and rate-limited login. Sessions expire after eight hours, are capped at 16 per user and store only random-token hashes. HTTPS cookies are `__Host-` prefixed, Secure, HttpOnly and SameSite=Strict. Cookie mutations require matching HTTPS Origin/Host; loopback HTTP is the development exception. Reload resumes a valid session. Browser storage never contains credentials. API tokens are shown once, expire after 1-365 days, are capped at 20 per user and are hashed at rest. Use dedicated publisher/reader users for scripts; the 64-hex bearer contract remains compatible.

Routes: `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/session` (principal or null), authenticated `GET /api/v1/session`, `PUT /api/v1/account/password`. Admin routes: `GET/POST /api/v1/admin/users`, `PUT .../users/{id}`, `PUT .../users/{id}/password`, `DELETE .../users/{id}/sessions`, `GET/POST .../users/{id}/tokens`, `DELETE .../users/{id}/tokens/{tokenId}`. Responses/audit omit password hashes and secrets. Editing the current admin may revoke its own session immediately.

## Host Installation

Install `/usr/bin/restic` and `/usr/bin/rclone` (SMB requires rclone >= 1.60) on the Linux host, not the web container. The existing protected agent serializes updates/backups. Fixed commands need no SMB mount, web Docker socket or additional web capabilities.

Provision a random 32-byte binary key at `/etc/device-update-hub/backup-key`, root-owned, group 1000, mode 0440, under protected root-owned ancestry. Never print/regenerate it while configuration depends on it; keep an external protected copy. Host policy adds both `backup_key_file` and `backup_config_directory` (`/etc/device-update-hub`). Merge [compose.backup.yaml](../compose.backup.yaml) with existing base/self-update overlays; `DUH_BACKUP_KEY_FILE` selects the host key path. Preserve the fixed Compose policy, active image override, existing mounts and loopback binding. The container receives only a read-only key file mount. These trusted host changes are separate from signed application packages.

Without key/exchange configuration, the web feature reports unavailable. With the host installed but no NAS settings, backups remain disabled. The agent validates protected policy/key ancestry. Manual operations require a fresh matching-key heartbeat. Restic/rclone and the host agent are maintained separately from application images.

## Synology Setup

Open **System > Synology backups**. Supply private LAN IPv4, existing share, repository subdirectory, dedicated least-privilege SMB user/password and optional domain. No destination was supplied during development; none is invented/contacted. Only SMB port 445 and safe names are allowed, not arbitrary URLs, commands or mount options. Require minimum **SMB 3 on Synology** and confirm it: rclone has no client-side minimum-dialect setting, so the Hub cannot independently attest the negotiated dialect. Do not use a NAS admin account.

Choose a recovery password of at least 16 characters and retain it **outside the VM**: losing it makes encrypted data irrecoverable. It differs from SMB/application passwords. Saved secrets are write-only; blank fields preserve them. Ordinary save rejects changing an existing repository's recovery password; rotation requires a controlled offline Restic procedure. Configuration is AES-256-GCM encrypted under the host key in the exchange inbox. Temporary child-process secrets use private files or stdin, not arguments/logs.

Save, **Test connection**, then **Back up now**. Connection testing checks share accessibility, not full write/restore capability or negotiated SMB dialect. Daily scheduling is opt-in at a configurable UTC time, one attempt per UTC day; retries after failure are explicit. Retention defaults to 7 daily, 4 weekly, 6 monthly and runs only after a successful snapshot/repository metadata check. It is not immutable/offline protection against a compromised backup writer; use independently secured NAS snapshots/copies as appropriate.

The agent checks access, journals the pinned current image/version, publishes maintenance, stops the writer, creates/fsyncs/compares the complete volume tar and copies protected host configuration. It restarts/verifies the same Hub before encrypted transfer. Snapshots include app credentials, users, settings, blobs and host policies/key. Workstation-only signing/SSH private keys need separate protected backups. Success removes the private local data copy; failure retains an available copy at `/var/lib/device-update-hub-updater/backup-{job-id}/source`, publishes sanitized failure and does not purge. Monitor space and retained failures; no local quota/automatic GC or off-host alerting is implemented.

Interrupted maintenance fails closed as `recovery_required`; interrupted transfer is failed without stopping the restarted Hub. UI/API show the latest job, not a full history explorer. Admin routes: `GET/PUT /api/v1/admin/backups`, `POST /api/v1/admin/backups/test`, `POST /api/v1/admin/backups/backup`. Queued/running/recovery-required work blocks configuration changes. Ordinary mutations return 503 during offline copying. Restore is an explicit operator procedure, not a web-triggered server replacement.

## Independent Restore

1. Use an isolated replacement host or stopped approved target, preserving original data/configuration. Install trusted Docker/Compose, Node/agent, Restic/rclone. Recreate protected SMB configuration and password file from independently retained recovery material; set `RCLONE_CONFIG`, `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE`. Never put secrets in arguments/logs/chat.
2. Run `restic snapshots`, then `restic check --read-data`. Select an explicit snapshot and `restic restore <snapshot-id> --target <empty-private-staging-directory>`. Inspect its hierarchy: backed-up source paths are preserved even when backup uses `.`. Never restore/extract directly into `/`.
3. Locate `source/backup/data.tar`, `source/host` and `source/deployment.json` in that hierarchy. Validate the archive and pinned image/version. Restore the complete tar into an empty stopped named volume, UID/GID 1000, with matching application/schema. Never mix database/blobs/WAL files across snapshots.
4. Restore host policies, credentials and encryption key with restrictive ownership/modes. Re-establish agent, fixed Compose/active image override and read-only trust/status/key mounts. Load the matching independently verified signed image if needed; the snapshot does not save the Docker daemon's entire image store.
5. Start the pinned image, verify exact health/schema, authenticate, inspect settings/manifests and compare downloaded artifact SHA-256. Validate only an approved gateway route. Enable scheduling after independent recovery succeeds.

For interrupted maintenance, stop the agent and inspect root-only recovery metadata/local data. Restart the recorded pinned image and verify health before acknowledging failure in private/shared backup status. Restore a complete copy with the writer stopped if needed. Never clear maintenance blindly. Isolated tests and update rollback do not certify live NAS backup/independent disaster restore; these remain acceptance gates until a real destination is configured.
