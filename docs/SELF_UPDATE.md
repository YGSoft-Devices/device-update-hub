# Hub Self-update

## Scope and Trust

Approved design: distribute the Hub as product `device-update-hub`, explicitly check/confirm in System, hand a complete signed package to a Linux/systemd host agent, stop/backup/replace/restart, then reload the browser after exact-version health verification. Generic device installers remain out of scope. The user subsequently authorized the designated Debian pilot and exact HTTPS route: real signed 0.1.0 -> 0.1.1 replacement, negative-version rollback with verified artifact hashes, systemd lifecycle and complete host reboot have passed there. See [DEPLOYMENT.md](DEPLOYMENT.md) for the active HTTPS route and remaining production gates. Windows tests still use fakes; other hosts need their own staging validation.

The web container never receives a Docker socket, host shell, root identity, signing key, writable host policy or writable agent status. A root-owned agent holds Docker access, which is effectively host-root authority and must be treated accordingly. Its installation/configuration requires an operator. Only fixed local Docker commands are executed; no commands, Compose documents, scripts or arbitrary destinations are accepted from packages. Publisher authentication is not a substitute for a package signature.

The host pins an Ed25519 public key independently of the Hub. Keep the private key on a protected signing/CI machine, never in the Hub, image, artifacts or repository. Key rotation requires coordinated trusted host/web configuration changes, not a self-published replacement key. Artifact SHA-256 protects transport; Ed25519 authenticates the exact metadata, including the image size, SHA-256, immutable Docker image ID, target, version/channel and database schema. Stable rejects prereleases; downgrades/replays are refused against the running version.

## Package and Publication

Each release contains exactly three required files:

- `hub-update.json`: bounded strict JSON, signed as its exact bytes. `schema_version: "1"`, product `device-update-hub`, canonical version/channel, exact target, `database_schema: 2`, image filename/size/SHA-256/ID. Unknown fields are rejected.
- `hub-update.sig`: raw 64-byte Ed25519 signature, not base64 or a secret key.
- `hub-image.tar`: a single-platform `docker save` archive of the application image. Image OS/architecture and immutable image ID are checked after loading; exact application version and database schema are checked after start.

The target is `hub-server` / `linux` / `amd64` (or `arm64`) / `docker` / updater protocol `1`. Both policy examples and release must match. Package schema 1 now permits database schemas 2 and 3; exact post-start health must match the signed schema. Application 0.2.0's approved additive migration requires a stopped schema-2 backup and separately updated host agent before installation. Rollback restores the complete old data before restarting the schema-2 image. Later schemas remain rejected. See [ADMINISTRATION.md](ADMINISTRATION.md).

The old 0.1.1 web also validates signed package schemas and rejects schema 3 before handoff. Its initial 0.2.0 migration therefore required an authenticated operator-confirmed atomic handoff to the upgraded agent, not pretending the new image uses schema 2. The agent still verifies the exact published bytes/signature/target, makes the offline copy and checks exact schema health. See the private-journal/copy locations and actual acceptance in [DEPLOYMENT.md](DEPLOYMENT.md). Future operators must plan both web and host compatibility; later normal installs through 0.2.0 support schemas 2/3.

Build the intended version from a pinned checkout after updating its package/application version and version inventory. That version must equal the signed version; file-header versions are separate. Example on a build machine with Docker:

```sh
docker build --tag device-update-hub:0.2.0 .
docker image inspect --format '{{.Id}}' device-update-hub:0.2.0
docker save --output .local/artifacts/hub-image.tar device-update-hub:0.2.0
```

Use [examples/hub-package.json](../examples/hub-package.json), replacing its all-zero image-ID placeholder with the actual inspect result and adapting version/architecture. Image paths resolve relative to the specification. Provision the Ed25519 key outside chat/logs; for example `openssl genpkey -algorithm ED25519 -out "$DUH_SIGNING_KEY_FILE"` under `umask 077`, then export only its public key with `openssl pkey -in "$DUH_SIGNING_KEY_FILE" -pubout -out updater-public.pem`.

```sh
export DUH_SIGNING_KEY_FILE=/protected/signing/updater-private.pem
npm run package:hub -- examples/hub-package.json .local/hub-package
npm run publish:release -- .local/hub-package/release-plan.json
```

The output directory must not already exist. Review release notes in the generated plan before publication. An administrator must have created the product and provisioned a dedicated product-scoped publisher credential. Existing `meeting-agent` publisher grants do not authorize Hub publication. The packaging command does not publish, install, generate production keys or contact GitHub. CI can run the same commands with an isolated signing secret and scoped publisher token; never expose those secrets to untrusted pull-request jobs.

No fixed 64 MiB ceiling remains. System controls the artifact-size cap (off by default) and upload deadline. Node/PowerShell publishers discover the policy; multipart uploads and host staging are streamed. Ensure reverse-proxy body limits/timeouts permit the chosen size. The reference browser's individual manual artifact download verifies an in-memory buffer; use the streaming Node downloader for large manual downloads. Self-update staging runs server-side, not in browser memory.

## Linux Host Installation

This is an operator procedure, not an automatic install script. Use a single Linux Docker Compose deployment, Node 24-26, Docker Compose v2 with `--wait`, `flock`, and sufficient local disk. The application image must include Node and GNU tar, as the supplied Dockerfile does. Current helper operations assume UID/GID 1000 and named volume `/var/lib/duh`; bind-mounted data or other UIDs require an independently reviewed adapter. Deploy this management-capable baseline manually before using self-update.

1. Back up the existing stopped Hub data and credentials separately. This revision atomically migrates database schema 1 to 2, adding settings without changing releases. Old schema-1 binaries cannot reopen schema 2; keep the pre-migration backup.
2. Install a trusted built agent checkout/dependencies under root-owned `/opt/device-update-hub-agent`. Build before installation; preserve `build/src`, `build/scripts` and production `node_modules`. The agent runs independently of the managed container and must not be overwritten by the package. The sample unit expects Node at `/usr/local/bin/node`, as installed by [bootstrap-debian.sh](../deployment/bootstrap-debian.sh).
3. Create root-owned `/etc/device-update-hub` (0755), `/var/lib/device-update-hub-exchange` (0755), and `/var/lib/device-update-hub-updater` (0700). Create exchange `inbox` owned by UID/GID 1000 (0700), and `status` owned by root (0755). These three directories must be disjoint, never ancestors of one another; their common parents must remain root-owned and not group/world writable. Only the inbox's contents are writable by the web process.
4. Install the trusted public key as `/etc/device-update-hub/updater-public.pem` (root-owned, 0644). Adapt [host-updater.json](../examples/host-updater.json) to the actual project, named volume, architecture, loopback health URL and protected paths; install it as `/etc/device-update-hub/updater.json` (0600). Adapt [web-update.json](../examples/web-update.json), using container paths; install it as `/etc/device-update-hub/web-update.json` (0644). All configuration ancestry must be root-owned and protected; symlinked configuration is refused by the agent.
5. Combine [compose.yaml](../compose.yaml) with [compose.self-update.yaml](../compose.self-update.yaml), using absolute environment paths `DUH_UPDATE_ROOT=/var/lib/device-update-hub-exchange` and `DUH_UPDATE_CONFIG_DIR=/etc/device-update-hub`. Render the combined configuration into a protected `/etc/device-update-hub/compose.yaml` using `docker compose --project-name device-update-hub --file compose.yaml --file compose.self-update.yaml config`. Review the rendered mounts, secret-file path and actual named volume before deployment; the output contains paths, not secret-file contents. Do not overwrite the source Compose file or redirect secrets into the repository. The combined file is the agent's fixed Compose input.
6. Deploy this baseline with the same Compose project name and the combined file. Confirm `/health` returns the installed version, database schema 2 and `status: "ok"`. Confirm the container has only a writable inbox, a read-only status mount and read-only configuration/key mounts, never a Docker socket.
7. Install [device-update-hub-updater.service](../deployment/device-update-hub-updater.service) into `/etc/systemd/system`, review its paths, then run `systemctl daemon-reload` and `systemctl enable --now device-update-hub-updater` with operator privileges. The unit uses `flock` for process exclusivity. Its sandbox is defense in depth; Docker access is still privileged. Do not run a second agent manually outside that lock.
8. Confirm `systemctl status` / `journalctl -u device-update-hub-updater` and System's installed version. A fresh agent heartbeat must match target/channel/key before installation is enabled. Verify the entire successful/failing update and restoration workflow on staging before enabling it on an important server.

Development tests never install services or replace a host. The separately authorized Debian deployment has executed these operations on its designated target only. Its exact `https://updatehub.ygsoft.fr` origin was subsequently activated with verified TLS. The external proxy and filtered host Nginx gateway remain outside Hub packages; keep Docker publication and updater health on loopback, and preserve the protected active Compose override. The gateway change did not rebuild frozen signed 0.1.1 or trigger another installation. Other deployment and generic production gates remain open.

## Runtime and Recovery

`GET /api/v1/admin/hub-update` returns configuration availability, agent readiness, installed version, target and current job. `POST .../check` returns an eligible release or null, without mutation/download. `POST .../install` requires `{release_id, confirmation: "exact-version"}` and returns 202 with a job. All three endpoints are admin-only. Discovery reuses product/channel/permission/target/SemVer selection; incomplete, withdrawn and incompatible releases are excluded. A repeated confirmation for the active release returns the same job.

The web process verifies artifact checksums/signature and copies into a UUID `.partial` directory, then atomically renames it `.ready` on the same filesystem. The agent ignores partial directories, snapshots metadata and image into its own 0700 storage, re-verifies them and refuses replay. `agent.json` and per-job/current status files are atomically written, synced and readable by the web container but not writable there. Keep the inbox/status mounts separate and never grant the container their parent directory.

Maintenance blocks mutations with 503 and `Retry-After`, but permits authenticated read/check/status and health requests. The host loads/verifies the new image before stopping the current service, checks that the configured named data volume matches the actual running mount, stops the writer, creates/syncs/compares an offline tar backup of the complete data volume, starts the immutable new image and verifies exact version/schema. No image is implicitly pulled from a registry. Active transfers may be interrupted and must retry; this is not zero-downtime deployment.

Private job directories retain the image, metadata/signature and `backup/data.tar`; private/per-job journals retain outcomes independently of the Hub database. Before stopping, a root-only synced `recovery.json` records the job/release, previous image/version, attempted image/version and backup directory. A backup path alone does not prove completion: check the durable job state and validate the archive. Completed inbox files are removed. Plan disk space for the catalog/artifacts, queued image, private image, expanded Docker image and complete data backup simultaneously. There is no automated retention/garbage collection or aggregate disk quota. Monitor space; never prune a running/in-flight backup or image. New host-agent versions are updated separately by an operator.

If the new start/health fails, the agent stops it, removes SQLite database/WAL/SHM files in the stopped volume, restores the offline snapshot, starts the previous image and verifies the previous version. Extra unreferenced blob/staging files may remain; no automated blob deletion is performed. If backup itself failed, no new version is started and the old image is restarted without restoring a partial backup. A failed rollback leaves `recovery_required` and maintenance active, rather than claiming success.

If the agent restarts with an active job, it marks recovery required and does not replay privileged steps. An operator must stop the agent and Hub, inspect the root-owned private journal and `recovery.json`, preserve the data as found, select a verified complete backup and trusted previous image, restore consistently, then start/verify the deployment. If interruption occurred before recovery metadata was written, the agent had not yet stopped or replaced the server. Use the agent's protected `deployment.json` override for lifecycle commands after a managed update; running the original build-only Compose configuration can recreate the old image. Do not clear maintenance or edit a job to success until the running version and data have been verified. Archive the interrupted ready request and explicitly mark the shared/private job as terminal with maintenance false only after recovery; restart the locked agent afterward. Never remove the data volume as an attempted repair.

The browser polls with bounded requests, keeps waiting across connection failures, displays rollback/recovery rather than success, and reloads only when the succeeded job, installed version and `/health` agree. Reload requires sign-in again; credentials and job tokens are not persisted in browser storage. A closed browser does not cancel the host job. Signing, unit tests and fake deployment tests are not certification of power-loss safety, production identity, filesystem durability or real Docker restoration.
